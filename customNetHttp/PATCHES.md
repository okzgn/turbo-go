# customNetHttp: Go's `net/http` with Turbo's patches

`customNetHttp` is the code of `net/http` from the Go version named in [`UPSTREAM`](UPSTREAM), merged into a single package and with Turbo's patches. It exists because several of Turbo's customizations can only be made inside `net/http`: for example, the response to a malformed request is written before any handler is reached, and the standard library doesn't allow changing it.

## What it contains

| Files | Source (in `GOROOT/src`) |
|---|---|
| `1.net.http.*.go` | `net/http`, `net/http/internal`, `net/http/internal/ascii`, `net/http/internal/httpcommon` |
| `a.server.cgi.host.go` | `net/http/cgi/host.go` (`cgi.Handler` becomes `CgiHandler`) |
| `c.mime.*.go` | `mime/multipart` |
| `x.net.http2.hpack.*.go`, `z.x.net.*.go`, `y.x.text.*.go` | `vendor/golang.org/x/net` (`http2/hpack`, `http/httpguts`, `http/httpproxy`, `idna`) and `vendor/golang.org/x/text` (what `idna` needs) |
| `0.turbo.shared.globals.go` | Own: what Turbo shares with the server (`TurboTimeLimits`, `TurboErrorTemplates`, `TurboMaxURILength`, `TurboMaxHeaderBytes`, `TurboMaxBodySize`, `TurboMaxFormParts`, `TurboMaxFormHeaders`, `TurboServerName`) |
| `0.turbo.patches.go` | Own: functions the patches call |
| `0.turbo.cgi.go`, `0.turbo.cgi_unix.go`, `0.turbo.cgi_linux.go`, `0.turbo.cgi_unix_other.go`, `0.turbo.cgi_windows.go` | Own: the output of the CGIs and their process group (a Job Object on Windows), used by P12 |
| `0.turbo.cgi_linux_test.go` | Own: test (Linux) that the leader of a CGI's group stays a zombie, keeping the group's ID, until the group is released |
| `0.turbo.cgi_unix_test.go` | Own: test (Unix) that the group of a CGI dies if the client leaves when the CGI has already finished |
| `0.turbo.cgi_test.go` | Own: test (Unix and Windows) that the group of a CGI can be killed until its output stops being read, also if the CGI has already finished |
| `0.turbo.godebug.go` | Own: substitute for `internal/godebug`: it doesn't read `GODEBUG` for the compatibility settings (each one is `""`, Go's default with the language version of `go.mod`, 1.26); the `http2debug` traces of Go's code do read it |

The files that start with `0.` are Turbo's; every other `*.go` is generated by [`regenerate`](regenerate/main.go) and is not edited by hand: a change in them is a patch.

Two manifests (`<sha256>  <file>`, as `sha256sum` writes them) pin what the tool doesn't regenerate:

- [`OWN.sha256`](OWN.sha256): the `0.*.go` files. `regenerate` rewrites it when it regenerates in this folder; `-check` fails if there is a `0.*.go` that is not in the list or that has changed, so any change in them shows in the diff of this file.
- [`SOURCES.sha256`](SOURCES.sha256): every Go file the package is regenerated from, by its path under `GOROOT/src`. `-update` writes it; in the other modes, if the `GOROOT` doesn't match it, the tool stops. The one for go1.26.10 was checked against the `go1.26.10` tag of the Go repository.

## Regenerating

From the repository root, with the Go version of `UPSTREAM` (the tool reads the `GOROOT` it runs with):

```bash
go run ./customNetHttp/regenerate -check   # customNetHttp == Go of UPSTREAM + patches, and the "go" line of go.mod is that version (used by release.sh and the checks of the README)
go run ./customNetHttp/regenerate          # rewrites the generated files
```

Every mode takes `-dir <folder>` to work on another copy of `customNetHttp` (by default, the one in the current directory).

The tool:

1. Copies the files of the packages in the table (without tests; those compiled on linux/amd64, and it fails if the selection differs in any of the reference contexts: linux/amd64, linux/arm64, windows/amd64, darwin/arm64 and freebsd/amd64, without cgo). The `//go:build` constraints of those files are kept, such as `!js`, `!wasm` or `!nethttpomithttp2`.
2. Merges them into the `customNetHttp` package: it type-checks each package with `go/types`, removes the qualifiers between them (`hpack.NewEncoder` → `NewEncoder`) and the corresponding imports, and if a package-level name clashes with another package, with one of Turbo's own names, with an imported package or with a predeclared identifier, renames it to `<package>_<name>` (`multipart.Reader` → `multipart_Reader`). `net/http` always keeps its names. `godebug.X` becomes `godebug_X`. Each file starts with a `// Source: …` line that says where it comes from.
3. Applies `patches/*.patch` in order. Each hunk must match exactly (only a shift of lines is accepted, never fuzzy context) and in a single place of the file; if one doesn't apply or matches in more than one place, it stops and says which.

### Updating to another Go version

When a Go version fixes `net/http`, `mime/multipart` or `x/net/http2`:

```bash
go1.26.N run ./customNetHttp/regenerate -update
```

It regenerates with that version, applies the patches and writes the version to `UPSTREAM`, the hashes of its sources to `SOURCES.sha256` and the version to the `go` line of `go.mod` (`go 1.26.N`: an older Go then downloads that one, or refuses to build with `GOTOOLCHAIN=local`, instead of mixing the fork with its own `crypto/tls` and `net/url`). The workflow `upstream.yml` fails while go.dev lists a newer Go of the same series. It takes neither `-output` nor `-patches`, and it doesn't go back to a version earlier than the one of `UPSTREAM` except with `-allow-downgrade`. If `-check` fails, `-update` is not the answer: either a Go other than the one of `UPSTREAM` is being used, or `customNetHttp` or its patches have changed. Before, check those sources against the official ones (the version's tag in the Go repository, or the `go1.26.N.src.tar.gz` from go.dev with its published SHA-256). If a patch doesn't apply, it has to be redone (see below) on the new base. Afterwards: `go build ./...`, `go vet ./...` and the whole test suite, including `turbo_patches_test.go`.

### Changing or adding a patch

The patches are unified diffs of the files of `customNetHttp` (paths `a/<file>` and `b/<file>`, relative to that folder), one per customization, and they are applied in order. `-patches N` applies only the first N. To change, for example, patch 06:

```bash
go run ./customNetHttp/regenerate -patches 5 -output /tmp/base   # base with patches 01-05
go run ./customNetHttp/regenerate -patches 6 -output /tmp/new    # edit the result here
cd /tmp && git diff --no-index base new -- '*.go'               # new 06: change the paths a/base/ and b/new/ to a/ and b/
```

The later patches must still apply; if not, they are redone the same way. `-patches N` requires `-output`, and `-output` only writes to an empty directory or to one that was already an output of the tool (it marks it with `.regenerate`), and only deletes the files it generated then. The patch reader is strict: each hunk has exactly the lines its `@@` header says and at least one of context, outside the hunks only git's headers of each file fit (`diff --git`, `index`…), and without any patch the tool stops.

With a clean repository it is enough to edit the generated files and save `git diff --relative=customNetHttp -- ':(glob)customNetHttp/[1-9a-z]*.go'` as a new patch at the end. Each change in Go's code carries a `turbo:Pn` comment; whatever can be written outside Go's code goes in `0.turbo.patches.go`. The patched files must be left as `gofmt` leaves them (regenerating fails otherwise) and `regenerate -check` must finish without differences.

## Patches

Each patch cites its tests with the file they are in (in the repository root).

### P1. Errors before the handler in HTTP/1 with Turbo's template

- **What it does:** the responses that `conn.serve` writes before reaching any handler (400 for a malformed request or a `statusError`, 431, 501 for an unknown `Transfer-Encoding`; the 414 of P3; and the 400 of a plain HTTP request to the TLS port) use Turbo's error template (`TurboErrorTemplates`) and carry `Server`, `X-Content-Type-Options: nosniff`, `Connection: close` and a `Content-Security-Policy` that allows no scripts and sandboxes the page (`turboErrorCSP`: no `meta` refresh, forms or windows either): the host of the request may be the panel's, and isn't always known yet. The 417 of an unknown `Expect` goes out through `Error`, and so with the template (P9).
- **Where:** `1.net.http.server.go`, `(*conn).serve`; `turboConnError`, `turboErrorCSP` and `turboErrorTemplate` in `0.turbo.patches.go`.
- **Why:** Turbo's error responses use a template configurable from the panel; Go writes a fixed text that can't be changed from outside. The template may be HTML, and the panel's session can set it without the password: on the panel's origin, its scripts must not run.
- **Patch:** `patches/01-P1-http1-errors.patch`. **Tests:** `TestT21_P1_HTTP1Errors` (`turbo_patches_test.go`), `TestRM1_ErrorsBeforeHandlerWithoutScripts` (`turbo_panel_host_test.go`).

### P2. HTTP/2 431 with the template

- **What it does:** `http2handleHeaderListTooLong` responds with the template (`turboWriteError`, which adds the `Content-Security-Policy` of P1) instead of Go's fixed HTML.
- **Where:** `1.net.http.h2_bundle.go`; `turboWriteError` in `0.turbo.patches.go`.
- **Why:** that of P1, in HTTP/2.
- **Patch:** `patches/02-P2-http2-errors.patch`. **Tests:** `TestT21_P2_HTTP2Limits` (`turbo_patches_test.go`), `TestRM1_ErrorsBeforeHandlerWithoutScripts` (`turbo_panel_host_test.go`).

### P3. URI length limit (`TurboMaxURILength`, setting `MUB`)

- **What it does:** in HTTP/1, `readRequest` returns `errTurboURITooLong` as soon as it reads the request line if the URI exceeds `TurboMaxURILength`, and `conn.serve` responds 414 with the template. In HTTP/2, `processHeaders` replaces the handler with a 414 with the template (`turboWriteError`, with the `Content-Security-Policy` of P1) if `:path` exceeds `TurboMaxURILength` (a 431 for truncated headers takes precedence, and a `:path` longer than `MUB` doesn't count towards `MHB`: see P5). In HTTP/1 `RequestURI` is measured as it arrives, so in an absolute-form request (`GET http://host/x`) the scheme and the host count too. In HTTP/2, a malformed `:path` (empty, or one Go can't read as a URI) is rejected earlier by Go as a stream error: `RST_STREAM` with `PROTOCOL_ERROR`, with no response, neither 400 nor 414.
- **Where:** `1.net.http.request.go` (`readRequest`), `1.net.http.server.go` (`(*conn).serve`), `1.net.http.h2_bundle.go` (`(*http2serverConn).processHeaders`); `turboErrorHandler` and `errTurboURITooLong` in `0.turbo.patches.go`.
- **Why:** Go doesn't limit the URI separately.
- **Patch:** `patches/03-P3-uri-limit.patch`. **Tests:** `TestT21_P1_HTTP1Errors` (`turbo_patches_test.go`), `TestT21_P2_HTTP2Limits` (`turbo_patches_test.go`), `TestP25_LimitsValueCopy` (`turbo_limits_test.go`).

### P4. Exact maximum size of the HTTP/1 headers (`TurboMaxHeaderBytes`, setting `MHB`)

- **What it does:** `(*Server).maxHeaderBytes` returns `TurboMaxHeaderBytes`, read once per request (`conn.turboReadLimit`, which the `StateActive` check also uses), without looking at `Server.MaxHeaderBytes`; `initialReadLimitSize` doesn't add Go's 4096 bytes of margin. The limit also holds for the following requests of a connection: the wait between requests (the `Peek` of `serve`) already reads with it, and the bytes that are in the buffer when a request starts to be read (from that wait, or from the previous request under *pipelining*) count towards it (`turboHeadersInBuffer`, which doesn't take the empty lines that may come after the body of a POST for the end of the headers); before, after the first request the real limit was `MHB` + 4096.
- **Where:** `1.net.http.server.go`.
- **Why:** so that `MHB` is the exact number of bytes of the header and applies without restarting.
- **Patch:** `patches/04-P4-http1-headers.patch`. **Tests:** `TestT21_P1_HTTP1Errors`, `TestN46_HTTP1KeepAliveHeaderLimit` and `TestRL_F2_HeaderLimitAfterPOSTEmptyLines` (`turbo_patches_test.go`), `TestP25_LimitsValueCopy` (`turbo_limits_test.go`).

### P5. HTTP/2 header limits (`TurboMaxHeaderBytes`)

- **What it does:** `readMetaFrame` limits the header list to `TurboMaxHeaderBytes`, counted as in Go and in HTTP/2 (name and value plus 32 bytes per field, `HeaderField.Size`; so a list of many small fields doesn't fit in the same budget as in HTTP/1), read once per header block. A single HPACK field can reach `turboMaxHeaderStringLen` (the largest of 64 KiB, `MHB` and `MUB`, with `SetMaxStringLength`): a field that exceeds `MHB` leaves the list truncated and its stream gets a 431 with the template (P2), and a `:path` that exceeds `MUB` is delivered outside the `MHB` budget so that P3 responds 414 (only the first of each block: another one, also one referenced from HPACK's dynamic table, counts like any field, so the block doesn't grow without limit); the connection keeps serving. Only a field larger than that cap, or a header fragment of more than twice what is left of the budget (as in Go), is a connection error. It keeps Go's separate budget for `Trailer`, also with `TurboMaxHeaderBytes`. In `SETTINGS_MAX_HEADER_LIST_SIZE` the server announces that same limit, `TurboMaxHeaderBytes` (`http2turboMaxHeaderBytes`), without the margin of `http2adjustHTTP1MaxHeaderSize`: as it is already counted in HTTP/2 units, a client that respects what is announced doesn't get a 431.
- **Where:** `1.net.http.h2_bundle.go`: `(*http2Framer).readMetaFrame`, `(*http2serverConn).maxHeaderListSize`. (The previous fork also modified `hpack.go`; that is no longer needed.)
- **Why:** the same limit as in HTTP/1, applicable without restarting.
- **Known limits:** `SETTINGS_MAX_HEADER_LIST_SIZE` is announced when the connection opens, but the current `MHB` is what applies: if it is lowered at runtime, a client that respects what was announced can get a 431 on the connections already open. `readMetaFrame` is also used by the package's HTTP/2 client, which Turbo doesn't use.
- **Patch:** `patches/05-P5-http2-headers.patch`. **Tests:** `TestT21_P2_HTTP2Limits` (`turbo_patches_test.go`), `TestC6_HTTP2FieldOverhead`, `TestH54_HTTP2AnnouncedHeaderLimit`, `TestN45_HTTP2FieldOverMHB` and `TestN72_HTTP2RepeatedLongPathCounts` (`turbo_patches_test.go`).

### P6. Timeouts (`RT`, `RHT`, `WT`, `IT`) read on each connection

- **What it does:** the HTTP/1 and HTTP/2 deadlines come from `TurboTimeLimits` (`atomic.Pointer[Timeouts]`) on each connection, request or stream, not from the fields of `Server`, so that a change in the panel applies without restarting. 0 means no limit, except for `RHT` and `IT`, which with 0 use `RT`, as Go does with `ReadHeaderTimeout` and `IdleTimeout` (`turboIdleTimeout` in `0.turbo.patches.go`). In HTTP/2, if `IT` is enabled while the connection is open, the idle timer is created when the last stream closes.
- **Where:** `1.net.http.server.go`: `tlsHandshakeTimeout`, `(*conn).readRequest`, `idleTimeout`, `readHeaderTimeout`. `1.net.http.h2_bundle.go`: `(*http2Server).serveConn`, `(*http2serverConn).serve`, `closeStream`, `processHeaders`, `upgradeRequest`, `newStream`.
- **Why:** so that the panel's settings apply at runtime, without restarting the server.
- **Patch:** `patches/06-P6-timeouts.patch`. **Tests:** `TestT21_P6_TimeoutsHTTP1` (`turbo_patches_test.go`), `TestB4_ZeroTimeoutsUseRT` (`turbo_patches_test.go`), `TestT04_HTTP2IdleTimeoutEnabledLater` (`turbo_fork_test.go`).

### P7. Don't drain an unread body

- **What it does:** `maxPostHandlerReadBytes = 0`, and the body is considered too large only if more bytes than that limit remain unread (Go compares with `>=`): if the handler left data unread from a body with `Content-Length`, the connection is closed instead of reading and discarding up to 256 KiB; if it read the whole body, the connection is reused, as in Go. An unread *chunked* body is still read to find its end (`CopyN`, as in Go), and if the handler closes it halfway (`earlyClose`) the keep-alive is lost.
- **Where:** `1.net.http.server.go`.
- **Why:** not to spend bandwidth on bodies nobody is going to use.
- **Patch:** `patches/07-P7-unread-body.patch`. **Test:** `TestT21_P7_UnreadBody` (`turbo_patches_test.go`).

### P8. `Server` header

- **What it does:** final responses carry a single `Server: OKZGN Turbo` header (`TurboServerName`), the internal ones too (errors, redirects of `ServeFile`): it replaces whatever the handler sets (a site's headers, a CGI) and doesn't depend on the handler setting `Date`. In HTTP/2 Turbo's `Server` isn't added to the trailers, and in HTTP/1 a `Trailer: Server` declared by the handler with `Header().Set` is ignored (`declareTrailer`). A `Server` trailer that a handler declares by other means (in HTTP/2, or with `Trailer:` keys in HTTP/1) is not filtered out, however: CGIs don't send trailers. Exception: the informational 1xx responses (`100 Continue`, `103 Early Hints`) go out as in Go, with the handler's headers as they are in HTTP/1 and, in HTTP/2, with Turbo's `Server`; Turbo doesn't send them itself.
- **Where:** `1.net.http.server.go` (`extraHeader.Write`, `(*chunkWriter).writeHeader`, `(*response).declareTrailer`), `1.net.http.h2_bundle.go` (`(*http2writeResHeaders).writeFrame`).
- **Patch:** `patches/08-P8-server-header.patch`. **Tests:** `TestT21_P8_ServerHeader` (`turbo_patches_test.go`), `TestC3_OneServerHeader` and `TestN47_ResponsesWithTemplate` (`turbo_patches_test.go`).

### P9. `Error` and `NotFound` with Turbo's template

- **What it does:** `Error` responds with the template of the code (`{TURBO_RESPONSE_CODE}`; HTML if it starts with `<`) and the detail on the next line, escaped with `html.EscapeString` if the template is HTML; `NotFound` adds no text of its own. The internal responses of `ServeFile` and `ServeContent` (400, 403, 404, 416, 500) use them too. Every response of `Error` carries the `Content-Security-Policy` without scripts, sandboxed, of the errors (`turboErrorCSP`), on every host: an error page needs none, and with `PA` empty the sites share the panel's origin, where a template with a script would run. The headers are set before `WriteHeader`, so that they reach the response.
- **Where:** `1.net.http.server.go`: `Error`, `NotFound`; `turboErrorTemplate` and `turboErrorCSP` in `0.turbo.patches.go`.
- **Patch:** `patches/09-P9-error-template.patch`. **Tests:** `TestT21_P9_ErrorTemplate` (`turbo_patches_test.go`), `TestC8_HTMLTemplateDetailEscaped` (`turbo_patches_test.go`), `TestW_ErrorHeaders` (`turbo_serving_test.go`), `TestRP_M02_ErrorTemplatesWithoutScriptsOnAnyHost` (`turbo_panel_host_test.go`).

### P10. Forms with `MBB` (`TurboMaxBodySize`), `TurboMaxFormParts` and `TurboMaxFormHeaders`; multipart in memory only

- **What it does:** the `x-www-form-urlencoded` body, which is kept whole in memory, is limited to `TurboMaxBodySize` and to 10 MiB at most, as in Go, and reading stops past that limit also when the body is already a larger `MaxBytesReader` (Go doesn't limit in that case); `FormValue`, `PostFormValue` and `FormFile` parse the multipart with `TurboMaxBodySize` (Go: 32 MB); `readForm` accepts at most `TurboMaxFormParts` parts (1000, as Go) and `TurboMaxFormHeaders` headers across all the parts (10 000, as Go, in `maxMIMEHeaders`: so 1 000 file parts fit, which carry two headers each), unless the request carries other maximums with `TurboWithFormLimits` (in `0.turbo.patches.go`; the authenticated file upload, `hardUpload`, uses it), and the whole form, files included, must fit in `maxMemory`, without Go's additional 10 MB or temporary files. A `maxMemory` of 0 or less (which in Go means "everything to temporary files") is `TurboMaxBodySize`. `TurboMaxFormParts` and `TurboMaxFormHeaders` are `atomic.Int64`: only the tests change them, but the requests read them concurrently.
- **Known limits:** the memory peak of a multipart can reach 2 or 3 times `maxMemory` while it is read (the parts and their copies); in Turbo it only happens in `hardUpload`, which requires a session.
- **Where:** `1.net.http.request.go` (`parsePostForm`, `ParseMultipartForm`, `FormValue`, `PostFormValue`, `FormFile`), `c.mime.formdata.go` (`readForm`), `c.mime.multipart.go` (`maxMIMEHeaders`, fields `turboMaxParts` and `turboMaxHeaders` of `multipart_Reader`).
- **Why:** the upload size is set by `MBB` and Turbo doesn't write temporary files (`hardUpload`).
- **Patch:** `patches/10-P10-forms.patch`. **Tests:** `TestT21_P10_Forms` (`turbo_patches_test.go`), `TestC4_ParseMultipartFormZero` (`turbo_patches_test.go`), `TestC7_URLEncodedFormLimit`, `TestH53_URLEncodedLimitWithMaxBytesReader` (`turbo_patches_test.go`), `TestC5_FormPartsLimit` (`turbo_parts_test.go`), `TestC5_HardUploadManyFiles` and `TestF04_ThousandFileParts` (`turbo_parts_test.go`), `TestP_HardUpload` (`turbo_panel_test.go`).

### P11. Own limit of `RST_STREAM` per second and connection

- **What it does:** `processResetStream` counts, in one-second windows (`turboRSTLimiter`), the connection's `RST_STREAM` frames that cancel an open stream (those of already finished streams don't count) and, above `turboMaxRSTStreamPerSecond` (4 times the concurrent streams the connection announces: 200 with Turbo's 50), closes the connection with `GOAWAY` (`ENHANCE_YOUR_CALM`). A browser that cancels everything it has in flight twice in a second doesn't reach it. It adds to Go's mitigation of the Rapid Reset attack (CVE-2023-44487).
- **Where:** `1.net.http.h2_bundle.go`: field `turboRST` of `http2serverConn`, `processResetStream`; `0.turbo.patches.go`.
- **Patch:** `patches/11-P11-rst-stream-limit.patch`. **Test:** `TestT21_P11_RSTStream` (`turbo_patches_test.go`).

### P12. `CgiHandler` with a timeout and errors with the template

- **What it does:** `Timeout` field: the process is started with `exec.CommandContext` (with the full path, so it isn't searched in `PATH`) and ends with the request or when `Timeout` passes (Turbo uses `WT`); if it expires before the headers, 504 with the template (Turbo delays the write deadline of the response until 2 s after the CGI's, in HTTP/1 and in HTTP/2, so that the 504 reaches the client). Every CGI error responds with the template and leaves the detail only in the log: a failure to start it, a *chunked* body (400; Turbo reads bodies of unknown length beforehand and passes `CONTENT_LENGTH`, so it doesn't come to happen), missing headers, no `Content-Type`, unreadable ones, a line of more than 16 KiB or more than 64 KiB in total, and a `Status` that isn't three digits from 200 to 599 (500, never an empty 200 nor a `WriteHeader` panic). A header the server has already put in the response (the site's) wins over the CGI's with the same name, which isn't added.
- **Processes the CGI leaves behind:** the process goes in its own group (Unix: `Setpgid`; Windows: a Job Object with `KILL_ON_JOB_CLOSE`, through `kernel32` and without dependencies, which it joins right after `Start`), and its output is read in a separate goroutine (`turboCGIOutput`, in `0.turbo.cgi.go`). What is guaranteed:
  - when `Timeout` passes or the request is cut off, the whole group is killed (the CGI and whatever it started) and reading stops at once; if part of the response had already been sent, it is cut off (`ErrAbortHandler`), so that it doesn't look complete;
  - if the response doesn't come out of the CGI (an error in its headers), the group is killed: the 500 doesn't wait for the CGI to finish, and on Windows the Job Object stays open until its output stops being read, so it reaches it even if the CGI has already finished;
  - if the CGI finishes and something it left running keeps its output open, the response is sent with what was received once 1 s passes without new data (on the monotonic clock: a change of the system time doesn't shorten it), counted at the earliest from when it finished (and from when the goroutine waits for data again, if a slow client held it), without killing anything; when reading stops the pipe is closed, which also on Windows cancels the pending read;
  - on Linux the leader of the group, once it ends, stays a zombie until the group is released (`waitid` with `WNOWAIT`, in `0.turbo.cgi_linux.go`), and the group is never killed after that: its PID is the group's ID, and reaped it could be given to another process, whose group a later kill reached; elsewhere it is reaped as soon as it ends;
  - nothing is guaranteed about a process that leaves the group (on Unix, one that creates its own group or session), nor on Windows about one the CGI starts before joining the Job Object (the instant between `Start` and the assignment).
  The input (`Stdin`) keeps `exec`'s `WaitDelay` of 1 s.
- **Where:** `a.server.cgi.host.go`: `CgiHandler`, `(*CgiHandler).ServeHTTP`.
- **Why:** to bound the running time of the CGIs and have their errors answered like Turbo's. (The body they receive is bounded by `main`, with `MaxBytesReader` and `MBB`.)
- **Patch:** `patches/12-P12-cgi.patch`. **Tests:** `TestW_CGIBodyAndEnv` (`turbo_serving_test.go`), `TestP27_CGIErrorDisclosure` (`turbo_serving_test.go`), `TestW_CGITimeout` (`turbo_serving_test.go`), `TestI08_SiteHeadersWinOverCGI` (`turbo_cgi_env_test.go`), `TestN44_CGITimeout504HTTP1`, `TestN44_CGITimeout504HTTP2`, `TestN48_CGIBadStatus`, `TestN48_CGILongHeaders` and `TestN47_CGIErrorsWithTemplate` (`turbo_cgi_errors_test.go`), and `TestN12_CGIChildDoesNotHoldResponse`, `TestN12_CGITimeoutKillsChild`, `TestN12_CGIClientGoneKillsChild`, `TestN70_CGISilentThenWritesAndExits`, `TestN73_CGIErrorDoesNotWaitForExit` and `TestN74_CGITimeoutAfterBodyIsNotComplete` (`turbo_cgi_children_test.go`, on Windows and on Linux).

### P13. 1 s deadlines for the HTTP/2 preface and first SETTINGS

- **What it does:** `http2prefaceTimeout` and `http2firstSettingsTimeout` are 1 s (Go: 10 s and 2 s): an HTTP/2 connection that doesn't send the preface or its first SETTINGS is closed after a second. `RHT` doesn't apply in that stretch, so this deadline is what limits a TLS connection that never gets to request anything.
- **Where:** `1.net.http.h2_bundle.go`, constants of `http2serverConn`.
- **Why:** the previous fork already had them so; they are kept as a documented patch.
- **Patch:** `patches/13-P13-http2-preface.patch`. **Test:** `TestT21_P13_HTTP2Preface` (`turbo_patches_test.go`).
